1 — Executive Summary

Die Architektur trägt. Die Gates darunter nicht.

Pi ist kein aufgeblähtes Projekt. Die Schichtung — harte Grenzen (workflow-policy) vor Stufenlogik (tool-policy) vor Dialog — ist sauber begründet, die LSP-Prozessverwaltung, die Electron-Trust-Grenze und die Plan-Handoff-Sanitisierung sind gute, notwendige Komplexität. Der überwiegende Teil des Codes verdient „Behalten".

Das Problem liegt eine Ebene tiefer: alle vier neuen Sicherheits- und Qualitätsgates hängen an einer einzigen Funktion, collectWorkspaceSnapshot(), und diese Funktion bricht reproduzierbar ab, sobald der Diff 1 MiB überschreitet — bei ~350 KB geänderten Textes. Die vier Aufrufer behandeln diesen Abbruch unterschiedlich: das Verifier-Commit-Gate öffnet stillschweigend, das Recovery-Gate schließt für immer, setup-core protokolliert gar nichts. Damit ist genau die Lücke, die AGENTS.md als „technisch erzwungen" beschreibt, durch einen großen Diff umgehbar — und ein großer Diff ist genau der Fall, für den das Gate gebaut wurde.

Daneben stehen zwei weitere bestätigte Fehlfunktionen desselben Musters: ein Verifier-Lauf ohne erkennbares Urteil blockiert die Wiederholung, während das Commit-Gate ihn korrekt ablehnt (Sackgasse), und der Verifikationsstatus erreicht die GUI nie, weil agent_settled vor der Zustandsaktualisierung an !ctx.hasUI abbricht.

Die Prüfinfrastruktur hat eine strukturelle Blindstelle: verify — das kanonische Pflichtprofil und der einzige CI-Schritt — führt npm test nicht aus. Der 1230-zeilige Frontend-Server und der Wire-Protocol-Contract laufen in keinem Gate. knip ist mit "exports": "off" konfiguriert und kann tote Exporte prinzipiell nicht sehen.

Empfehlung: keine Architekturumbauten. Drei chirurgische Korrekturen an der Snapshot-Schicht und am Verify-Profil beheben die gesamte P0/P1-Klasse.

3 — Architektur- und Nutzungskarte

Zehn reale Hauptpfade

1 · Installation und Start

scripts/install-user.mjs → ~/.pi/agent → npm ci → bin/pi (bash-Shim) → echtes pi-Binary via PATH

Seiteneffekt: Shim leitet nur gui um; findet er kein zweites pi auf PATH, exit 127. Zustandsquelle: PI_GUI_REAL_PI oder PATH-Scan.

2 · Normale CLI/TUI-Sitzung

settings.json → 13 Extensions → aurora-ui (TUI-Besitzer) ← EventBus ← plan-mode / setup-core / permissions / lsp

Sauber: genau ein UI-Besitzer (Entscheidung 007); Aurora ist Konsument, nie Datenquelle.

3 · Planmodus → Work

Shift+Tab → session.requestMode() → beginTurn() pinnt turnMode → plan_write → settleTurn() → readiness → /plan-approve → consumeApproval(hash+prompt) → buildPlanContextMessage()

Asymmetrie: Hash-Mismatch benachrichtigt die Nutzerin, Session-Mismatch verbraucht die Freigabe stumm (F-27).

4 · Berechtigung und Tool-Ausführung

tool_call → Trust-Gate → assessWorkflowTool (hart) → Web-Gate → Verifier-Gate → Debugger-Gate → Commit-Gate → Recovery-Gate → planModeMutationGuard → decideTool → Dialog

Neun Schichten in fester Reihenfolge. Zwei davon rufen synchron git auf (F-10); die harte Schicht macht Teile von decideFileAccess unerreichbar (F-09).

5 · Subagent und Verifier

subagent(agent:"verifier") → Vorlagenprüfung → Budget-Prüfung → Dedup gegen Fingerprint → input.acceptance erzwungen → tool_result → extractVerifierRunRecord → lastVerifierRun

Zustandsquelle nur im Speicher: lastVerifierRun überlebt keinen Sitzungsneustart. Urteilslose Läufe erzeugen die Sackgasse F-04.

6 · Session, Recovery, Kompaktierung

before_agent_start → Fingerprint → JSONL-Marker (turn-start / failure / turn-settled / recovery-required / recovery-checked) → latestRecoveryGate()

Doppelte Ableitung: recoverySnapshot() in index.ts und der tote Export gateBlocked() implementieren dieselbe Entscheidung (F-11).

7 · LSP

lsp/config (Binary an Builtin oder node_modules/.bin gebunden) → registry (single-flight) → process (SIGTERM→SIGKILL) → transport (eine settle()-Senke)

Vorbildlich: Timeout, Backoff, Cleanup und Prozessgruppen-Kill sind vollständig. Keine Befunde.

8 · GUI-Aufruf pi gui

bin/pi → bin/pi-gui → electron gui/ → BrowserWindow(sandbox, contextIsolation, nodeIntegration:false) → preload.cjs (21 Kanäle) → ipc-handlers (Pfad- und Protokollvalidierung)

Gehärtet: SAFE_EXTERNAL_PROTOCOLS, realpathSync-Basisprüfung für Session-Pfade, window-open und Navigation verweigert.

9 · GUI ↔ Bridge ↔ Kern

frontend-server (JSONL, spawn pi --mode rpc) ⇄ pi-rpc-manager ⇄ frontend-bridge (PI_FRONTEND_RPC=1) ⇄ EventBus-Kanäle aurora-ui/state/*

Leere Telemetrie: das Feld verification bleibt in diesem Pfad dauerhaft null (F-05). Vier separate Definitionen von WorkflowMode auf der Strecke (F-14).

10 · Verifikation und Benchmark

project_check(profile:"verify") → .pi/verify.json → npm --prefix npm run verify → format:check · typecheck · deadcode · test:coverage · test:patches · test:gui · audit:check

Lücke: npm test ist kein Teil davon — Protokollpaket und Frontend-Server laufen weder in verify noch in CI (F-07).

F-01

Das Verifier-Commit-Gate öffnet stillschweigend, sobald der Diff 1 MiB überschreitet

P0Confidence hoch
Kategorie: Sicherheitsgrenze umgehbar · Fail-openAufwand: kleinÄnderungsrisiko: niedrig
Dateien
shared/workspace-snapshot.mjs:9 (git(), execFileSync ohne maxBuffer) · extensions/permissions/verifier-policy.ts (assessGitCommitVerifierGate, catch → PERMITTED)
Beobachtet
collectWorkspaceSnapshot() wirft ENOBUFS. Der Aufrufer fängt jede Ausnahme ab und gibt PERMITTED zurück. git commit läuft durch, ohne dass ein Verifier-Lauf existiert — ohne Meldung, ohne Log, ohne Session-Eintrag.
Erwartet
AGENTS.md: „git commit wird technisch blockiert, wenn der Diff eine dieser Dateien berührt und kein verifier-Lauf mit Urteil PASS vorliegt." Ein Gate, das seine Evidenz nicht erheben kann, darf nicht schweigend zur Erlaubnis werden.
Ursache
Node setzt für execFileSync ein maxBuffer von 1 MiB. git diff --binary überschreitet das bei etwa 350 KB geändertem Text (eine Vollersetzung erzeugt alte + neue Zeilen) oder bei jeder binären Änderung über ~700 KB.
Auswirkung
Genau der große, riskante Diff, für den das Gate 2026-08 eingeführt wurde, umgeht es. In diesem Repository ist die Schwelle trivial erreichbar: benchmarks/real-duel/reports/real-01-tui-warm-theme/pi_transcript.txt ist allein 5,4 MB.
Nachweis
Reproduziert in einem Wegwerf-Repo im Scratchpad:
$ git init repro && ...          # Datei mit 400 KB, dann vollständig ersetzt
$ git diff --no-ext-diff --binary -M | wc -c
1228907
$ node -e "collectWorkspaceSnapshot('repro')"
THROWS: ENOBUFS  spawnSync git ENOBUFS

# 900 KB -> 2764907 Bytes -> ENOBUFS
# 1100 KB -> 3379307 Bytes -> ENOBUFS
Maßnahme
Ein maxBuffer setzen (z. B. 64 MiB) und — wichtiger — den Diff-Hash streamen statt zu puffern. Unabhängig davon: der catch-Zweig darf nicht PERMITTED liefern, sondern muss ein sichtbares „Gate nicht auswertbar" erzeugen (blockieren mit nennbarem Grund, wie recovery_check es bereits tut).
Betroffene Tests
tests/suites/runtime/verification.mjs („verifier coverage capability bridge"), tests/suites/runtime/resilience.mjs. Neu nötig: ein Negativtest mit einem Diff > 1 MiB.
F-02

Derselbe Fehler sperrt den Agenten dauerhaft aus dem Recovery-Gate aus

P0Confidence hoch
Kategorie: Kernfunktion unzuverlässig · DeadlockAufwand: kleinÄnderungsrisiko: niedrig
Dateien
extensions/resilience/index.ts (workspaceFingerprint() → "unavailable"; recovery_check.execute() wirft) · extensions/permissions/guards.ts (recoveryGateBlocks)
Beobachtet
Nach einem fehlgeschlagenen Turn mit großem Diff: workspaceFingerprint() liefert "unavailable", workspaceChanged() ist damit dauerhaft true, das Gate bleibt scharf. recovery_check — die einzige Entsperrung — wirft ebenfalls und meldet „Die Schreibsperre bleibt bestehen".
Erwartet
Das Gate ist entsperrbar, sobald der Workspace geprüft wurde.
Ursache
Gleiche ENOBUFS-Wurzel wie F-01, hier aber fail-closed. Das Gate blockiert write, edit und jedes nicht-diagnostische bash — also auch git stash, git checkout und alles, womit der Diff verkleinert werden könnte.
Auswirkung
Der Agent ist schreibunfähig und kann die Ursache nicht selbst beseitigen. Ausweg existiert nur für den Menschen: ein selbst getipptes !git stash läuft am Recovery-Gate vorbei, weil der user_bash-Pfad es nicht auswertet. Die UI zeigt lediglich „⚠ Recovery-Check offen" und nennt die eigentliche Ursache nie.
Nachweis
Wurzelursache reproduziert (F-01); die Fortpflanzung ist im Quelltext lückenlos: catch { return "unavailable" } → workspaceChanged() → recoverySnapshot().armed = true → recoveryGateBlocks() → { block: true }.
Maßnahme
Wie F-01 an der Wurzel. Zusätzlich: der Fehlertext von recovery_check muss die Snapshot-Ursache und den Menschen-Ausweg nennen, statt nur „bleibt bestehen".
Betroffene Tests
tests/suites/runtime/resilience.mjs; kein bestehender Test deckt einen Snapshot-Fehler ab.
F-03

Dieselbe Snapshot-Störung wird in drei Modulen dreifach verschieden behandelt

P1Confidence hoch
Kategorie: widersprüchliche VerantwortlichkeitAufwand: kleinÄnderungsrisiko: mittel
Dateien
extensions/permissions/verifier-policy.ts · extensions/resilience/index.ts · extensions/setup-core/index.ts:303
Beobachtet
Drei Konventionen für ein und denselben Ausnahmefall:
verifier-policy.ts   catch { return PERMITTED }        -> fail-open   (Gate aus)
resilience/index.ts  catch { return "unavailable" }    -> fail-closed (Gate an, für immer)
setup-core/index.ts  catch { return undefined }        -> stumm       (lastVerifierRun nie gesetzt)
Erwartet
Eine Konvention, an einer Stelle festgelegt — ein { ok, snapshot, reason }-Ergebnis statt drei Interpretationen einer geworfenen Ausnahme.
Auswirkung
Bei großem Diff ist ein bestandener Verifier-Lauf nicht aufgezeichnet (setup-core stumm), das Commit-Gate gleichzeitig abgeschaltet (fail-open) und das Recovery-Gate gleichzeitig unlösbar (fail-closed). Drei Gates, drei Richtungen, ein Auslöser — und keine einzige Meldung.
Maßnahme
collectWorkspaceSnapshot um eine explizite Ergebnisform erweitern; jeder Aufrufer entscheidet dann sichtbar und begründet. Reine Vereinfachung mit Verhaltenskorrektur, keine neue Abstraktion.
Betroffene Tests
verification.mjs, resilience.mjs, setup-core.mjs
F-04

Ein Verifier-Lauf ohne erkennbares Urteil blockiert seine eigene Wiederholung

P1Confidence hoch
Kategorie: Zustandssackgasse · leere TelemetrieAufwand: kleinÄnderungsrisiko: niedrig
Dateien
extensions/setup-core/subagent-output-guard.ts (extractVerifierRunRecord) · extensions/permissions/verifier-policy.ts (assessVerifierDedup vs. assessVerifierCoverageForDiff)
Beobachtet
Endet ein Verifier-Lauf sauber (exit 0), enthält seine Ausgabe aber keinen führenden PASS/FAIL/UNVERIFIABLE-Token, entsteht der Datensatz { status: "completed", verdict: undefined }. Die beiden Konsumenten lesen ihn gegensätzlich:
assessVerifierCoverageForDiff:  verdict === "PASS" || "PASS_WITH_WARNINGS"  -> nicht gedeckt, Commit bleibt gesperrt  ✔ richtig
assessVerifierDedup:            verifierStatus !== "completed" ? PERMITTED  -> blockiert den zweiten Lauf            ✘ falsch

Blocktext: "Diff ist seit dem letzten abgeschlossenen Verifier-Lauf
            unverändert (Urteil: undefined)."
Erwartet
Ein Lauf ohne Urteil ist genau das, was AGENTS.md „ein ergebnisloser verifier-Lauf" nennt — er zählt nirgends als Verifikation und darf die Wiederholung nicht sperren.
Ursache
assessVerifierDedup prüft nur status, assessVerifierCoverageForDiff prüft status und verdict. Die Deduplizierungslogik wurde in 388f39f nachgerüstet, ohne die Urteilsbedingung mitzunehmen.
Auswirkung
Sackgasse: nicht committierbar (kein PASS) und nicht erneut prüfbar (Dedup). Ausweg nur, wenn der Agent den Abschnitt „Grund für erneute Prüfung" errät — der Blocktext nennt ihn zwar, aber der Zustand ist kein Grund, sondern ein Fehler. Der interpolierte Text Urteil: undefined ist das sichtbare Symptom.
Nachweis
Statisch eindeutig belegt: verifier-policy.ts Zeile „if (verification.verifierStatus !== "completed") return PERMITTED;" gegen subagent-output-guard.ts „if (verdict) record.verdict = verdict;" — verdict bleibt bei status: "completed" optional.
Maßnahme
In assessVerifierDedup zusätzlich auf ein vorhandenes Urteil prüfen. Zwei Zeilen.
Betroffene Tests
tests/suites/runtime/verification.mjs — der Fall „completed ohne Urteil" fehlt vollständig.
F-05

Der Verifikationsstatus erreicht die GUI nie

P1Confidence hoch
Kategorie: asymmetrischer Kontrollpfad · leere TelemetrieAufwand: kleinÄnderungsrisiko: niedrig
Dateien
extensions/setup-core/index.ts:396 im agent_settled-Handler
Beobachtet
Der aktivierte Zweig bricht bei !ctx.hasUI ab, bevor lastSettledStatus gesetzt und publishAuroraVerification() aufgerufen wird. Der deaktivierte Zweig darüber publiziert in derselben Lage sehr wohl.
if (!statusEnabled) {
  ...
  publishAuroraVerification();      // publiziert auch ohne UI
  return;
}
const status = verificationStatus(workspaceSnapshot(ctx.cwd), ...);   // teuer: 7 git-Prozesse
if (!ctx.hasUI) return;                                                // und dann verworfen
lastSettledStatus = status;
publishAuroraVerification();
Erwartet
Der Zustandsvertrag ist laut state-contract.ts präsentationsneutral: „Aurora ist Konsument wie jedes andere Frontend". Ein Frontend ohne TUI muss dieselben Felder bekommen.
Ursache
Die hasUI-Prüfung schützt ctx.ui.setStatus, steht aber vor der Zustands- und Bus-Aktualisierung statt nur vor dem TUI-Aufruf.
Auswirkung
Im GUI-Pfad (PI_FRONTEND_RPC=1, kein TUI) bleibt state.verification dauerhaft null: die Desktop-Oberfläche zeigt nie einen Verifikationsstatus. auroraVerificationSnapshot() gibt wegen lastSettledStatus === undefined für immer null zurück. Zusätzlich wird bei jedem agent_settled ein vollständiger Snapshot (7 synchrone git-Aufrufe) erhoben und weggeworfen.
Nachweis
Statisch eindeutig. frontend-bridge/index.ts aktiviert sich nur bei PI_FRONTEND_RPC === "1"; in diesem Modus existiert kein TUI-Kontext. Die einzigen beiden publishAuroraVerification()-Aufrufe liegen in diesem Handler.
Maßnahme
if (!ctx.hasUI) return; entfernen und stattdessen nur den ctx.ui.setStatus-Aufruf mit ctx.hasUI bewachen — wie es der deaktivierte Zweig bereits tut.
Betroffene Tests
tests/suites/runtime/frontend-bridge.mjs, setup-core.mjs — beide prüfen den Handler bisher nur mit UI.
F-06

project-write erlaubt beliebige Schreibzugriffe außerhalb des Projekts über Interpreter — YOLO nicht

P1Confidence hoch
Kategorie: asymmetrische Stufenlogik · ProjektgrenzeAufwand: mittelÄnderungsrisiko: mittel
Dateien
extensions/shared/permission-policy.ts — decideBash(), likelyExternalWrite(), isWriteCapableCommand(), opaqueInterpreter()
Beobachtet
Auf der Standardstufe project-write (Default bash: "allow", bestätigt in setup-core/config.ts:55) fällt ein Kommando wie node -e "require('fs').writeFileSync('/home/user/.bashrc', x)" durch alle Muster hindurch auf ALLOW. Auf yolo wird derselbe Aufruf durch opaqueInterpreter() hart geblockt.
Erwartet
Die Stufenordnung sollte monoton sein. Eine Stufe namens project-write darf nicht mehr außerhalb des Projekts schreiben dürfen als die als „temporärer Bypass" bezeichnete Stufe darüber.
Ursache
likelyExternalWrite() setzt isWriteCapableCommand() voraus, und dessen Regex kennt nur Shell-Werkzeuge (rm|cp|mv|tee|dd|ln|sed -i, Redirections). Ein Interpreter, der über sein eigenes API schreibt, erfüllt keines dieser Muster. referencesSystemPath() greift nur für /etc /usr /bin /sbin /boot /var — das Home-Verzeichnis der Nutzerin ist nicht darunter.
Auswirkung
Die Zusage „Änderungen bleiben im Projekt" gilt auf der meistgenutzten Stufe nicht. Kein Angriffsszenario nötig: ein Skript, das versehentlich nach ~ schreibt, läuft ohne Rückfrage durch. Der Effekt ist zugleich verwirrend, weil ein Wechsel auf YOLO die Fähigkeit entzieht.
Nachweis
Statisch eindeutig: decideBash durchläuft für project-write nacheinander isSensitiveReference (nein), CRITICAL_BASH_PATTERNS (nein), referencesSystemPath (nein), SENSITIVE_ASK_PATTERNS/ROUTINE_ASK_PATTERNS (nein), containsUnquotedVariableExpansion (nein), likelyExternalWrite (nein) und endet auf return ALLOW.
Maßnahme
Entscheidung erforderlich, nicht nur ein Patch: entweder opaqueInterpreter() auch auf project-write als ask auswerten (kostet Bedienkomfort bei node script.js), oder die Zusage in der Dokumentation auf das reduzieren, was durchgesetzt wird. Nicht ohne Freigabe umsetzen.
Betroffene Tests
tests/workflow-mode/permissions.test.mjs — enthält keinen Negativtest für Interpreter-Schreibzugriffe auf irgendeiner Stufe.

F-09

Die harte Grenze macht die Hälfte von decideFileAccess unerreichbar — und hebt ihre eigene Ausnahme wieder auf

P1Confidence hoch
Kategorie: widersprüchliche Verantwortlichkeit · toter ZweigAufwand: mittelÄnderungsrisiko: mittel
Dateien
extensions/permissions/workflow-policy.ts (assessWorkflowTool) · extensions/shared/permission-policy.ts (decideFileAccess) · extensions/permissions/guards.ts
Beobachtet
assessWorkflowTool blockiert für jedes Tool mit path und auf jeder Stufe alles außerhalb des Projekts sowie jeden Symlink-Ausbruch. Es läuft in guards.ts als zweite Prüfung, lange vor decideTool. Damit sind in decideFileAccess vier Zweige unerreichbar: Lesen außerhalb des Projekts, Symlink-Schreibzugriff, Systempfad-Schreibzugriff und externer Schreibzugriff — rund 40 Zeilen mit differenzierter ask/deny-Logik pro Stufe.
Erwartet
Entweder die Feinlogik greift, oder sie steht nicht da. Beides gleichzeitig zu pflegen erzeugt Regeln, die nur Regeln anderer Regeln kompensieren.
Ursache
Die harte Schicht wurde nachträglich vor die Stufenschicht gezogen, ohne die dort verbliebene Duplikatlogik zu entfernen.
Auswirkung
Zwei Effekte. Erstens Wartungsgefahr: tests/workflow-mode/permissions.test.mjs:73 prüft decideFileAccess direkt und erzeugt Vertrauen in einen Pfad, den die Produktion nie nimmt — genau die Fehlerklasse „Tests auf Implementierungsdetails". Statisch eindeutig: decideFileAccess hat außerhalb von tool-policy.ts und einem Test keine Aufrufer; die Reihenfolge in guards.ts ist unbedingt.

Die unerreichbaren Zweige entfernen und die Runtime-Docs-Ausnahme in decideFileAccess spiegeln — oder die Ausnahme streichen, falls sie nicht mehr gebraucht wird.
Betroffene Tests
tests/workflow-mode/permissions.test.mjs muss von decideFileAccess auf den vollständigen Guard-Durchlauf umgestellt werden.

Bestätigt, belegt, vermutet — und was sich nicht bestätigt hat

Bestätigt reproduziert

  • F-01 — ENOBUFS ab 1 MiB Diff, dreimal in Folge in einem Wegwerf-Repo im Scratchpad; Byte-Grenze und Fehlercode oben protokolliert.

Statisch eindeutig belegt

  • F-02 bis F-05, F-07 bis F-18, F-20 bis F-22, F-25, F-26, F-28 — jeweils eine unbedingte Codestelle oder ein zählbarer grep-Nachweis; die Aufruferketten sind vollständig verfolgt.
  • F-06 — jede Regel in decideBash einzeln gegen das Beispielkommando geprüft; der Default bash: "allow" ist in config.ts:55 und im Test target-config.mjs:299 festgeschrieben.

Plausibler Verdacht — Nachweis offen

  • F-19 — die gemischte Pfadbasis ist aus den git-Konventionen abgeleitet, aber nicht in einem Unterverzeichnis-Lauf gemessen. Nachweis: pi aus einem Unterordner starten, eine neue Datei unter extensions/permissions/ anlegen, prüfen ob das Commit-Gate greift.
  • F-23 — ob 0.84.4 die Patch-Anker verschiebt, ist ohne installierte Runtime nicht feststellbar.
  • F-27 — resetForSession() löscht die Freigabe beim Sitzungswechsel; der Session-Mismatch-Zweig ist möglicherweise unerreichbar. Vor einer Änderung Erreichbarkeit klären.

Geprüft und widerlegt

  • Symlink-Lesegrenze: decideFileAccess prüft Symlink-Ausbrüche tatsächlich nur beim Schreiben — der naheliegende Schluss auf eine Leselücke ist aber falsch: assessWorkflowTool blockiert vorher auf jeder Stufe. Der Befund reduziert sich auf die tote Redundanz F-09.
  • Nicht-reguläre untracked Dateien: Hypothese war, dass eine FIFO untrackedContentFingerprints() zum Werfen bringt. Im Reproduktionsrepo geprüft: git ls-files --others listet FIFOs nicht auf, der Snapshot lief durch. Kein Befund.

10 — Vorgeschlagene Zielstruktur

Kleine Verschiebungen, keine Umbauten

Die bestehende Ordnung ist tragfähig. Vier Präzisierungen genügen:

  1. Eine Snapshot-Schicht mit expliziter Fehlerform. shared/workspace-snapshot.mjs bleibt, wo es ist, gibt aber { ok: true, snapshot } | { ok: false, reason } zurück und memoisiert pro Turn. Alle vier Aufrufer entscheiden danach sichtbar. Das ist die Wurzel von F-01 bis F-03, F-10 und F-19.
  2. Eine Besitzerin je Grenze. Projekt- und Symlink-Grenze gehören assessWorkflowTool; decideFileAccess entscheidet nur noch innerhalb des Projekts. Damit fallen die toten Zweige und der Widerspruch um die Runtime-Docs-Ausnahme weg (F-09).
  3. Eine Quelle je Aufzählung. WorkflowMode, PermissionLevel und die Shortcut-Tabelle leben genau einmal im Wire-Protokollpaket; extensions/, frontend-server/ und gui/renderer/ importieren oder werden gegen sie geprüft (F-14, F-16). Der Name frontend-protocol wird für genau eines der beiden Module frei (F-15).
  4. Ein Pflichtprofil, das den ganzen Prüfstand nennt. verify nimmt test:protocol-package und test:frontend-server auf; knip aktiviert die exports-Regel (F-07, F-11).

Ausdrücklich nicht vorgeschlagen: eine Zusammenlegung von CLI/TUI und GUI, ein Umbau der Guard-Reihenfolge, eine Reduktion der Berechtigungsstufen oder eine Auslagerung der Benchmarks. Für keines davon liefert diese Analyse einen Grund.

11 — Priorisierter Folgeplan

Drei Pakete, in dieser Reihenfolge

Die Nummerierung ist eine echte Abfolge: Paket B baut auf der in Paket A bereinigten Snapshot-Schicht auf, Paket C braucht vorher eine Freigabe.

PAKET A — SOFORTIGE P0/P1-KORREKTUREN

Die Snapshot-Wurzel und die vier Gates darauf

  • F-01 + F-02 + F-03 — collectWorkspaceSnapshot mit maxBuffer und gestreamtem Patch-Hash; explizite Ergebnisform; alle vier Aufrufer auf eine einheitliche, sichtbare Behandlung umstellen. Ein ausgefallener Snapshot blockiert das Commit-Gate mit nennbarem Grund, statt es zu öffnen.
  • F-04 — assessVerifierDedup prüft zusätzlich auf ein vorhandenes Urteil.
  • F-05 — hasUI-Guard in agent_settled auf den setStatus-Aufruf beschränken.
  • F-08 — gitSubcommand() auf executableToken() umstellen.
  • F-07 — beide fehlenden Testskripte in verify aufnehmen.

Abschlusskriterien: Ein Diff > 1 MiB, der eine verifier-required-path-Datei berührt, blockiert git commit mit sichtbarem Grund. recovery_check entsperrt dasselbe Repository. Ein urteilsloser Verifier-Lauf lässt sich wiederholen. Die GUI zeigt einen Verifikationsstatus. /usr/bin/git commit löst das Gate aus. project_check({profile:"verify"}) läuft grün und enthält Protokollpaket sowie Frontend-Server.

Regressionstests: neuer Snapshot-Negativtest (>1 MiB) in verification.mjs und resilience.mjs; „completed ohne Urteil" in verification.mjs; agent_settled ohne UI in frontend-bridge.mjs; Kommandovarianten für bashTouchesGitCommit. Dieses Paket berührt extensions/permissions/** und extensions/setup-core/index.ts — beide stehen in verifier-required-paths.ts, eine Verifier-Delegation ist also Pflicht.

PAKET B — RISIKOARME VEREINFACHUNGEN

Duplikate zusammenführen, Totes entfernen, Doku angleichen

  • F-09 — unerreichbare Zweige in decideFileAccess entfernen, Runtime-Docs-Ausnahme spiegeln, Tests auf den Guard-Durchlauf umstellen.
  • F-10 — Fingerprint pro Turn memoisieren (setzt Paket A voraus).
  • F-11 — knip-Regel exports aktivieren, die ~50 Treffer meiner Vorabprüfung einzeln triagieren, gateBlocked entweder nutzen oder streichen.
